# T-E5 Experiment: DWA Controller Delay

Experiment T-E5 evaluates the effects of a controlled software delay introduced directly into the DWA local controller of the ROS Navigation Stack.

The purpose of the experiment is to determine how suspending the local controller affects:

* controller execution periodicity;
* velocity-command publication frequency;
* motion continuity;
* navigation performance;
* the robot's ability to complete the assigned navigation task.

The delay is inserted at the beginning of:

```cpp
DWAPlannerROS::computeVelocityCommands()
```

The suspension occurs before the controller obtains the current robot pose and computes the next velocity command.

Hence, while the controller is suspended, odometry, sensor measurements, localization information, and costmap data may continue to evolve, but no new velocity command is generated by the DWA planner.

## Experimental configuration

The experiment uses:

* ROS Noetic;
* Gazebo;
* TurtleBot3 Burger;
* the `turtlebot3_world` simulation environment;
* the ROS Navigation Stack;
* the DWA local planner;
* the same static map, initial pose, navigation goal, and termination criteria used by the other TurtleBot3 experiments;
* source-level timing instrumentation inside the DWA controller;
* a controlled delay applied at the beginning of the controller cycle;
* a custom CSV logger for internal controller timing measurements;
* ROS bag recording for externally observable navigation behavior.

The tested delay conditions are:

```text
0 ms
200 ms
500 ms
1000 ms
2000 ms
```

The 0-ms configuration retains the complete source-level instrumentation and logging code without introducing an intentional suspension.

It is the matched instrumented baseline used to evaluate the delayed conditions.

## Injection point

The modified execution sequence is conceptually:

```text
DWAPlannerROS::computeVelocityCommands()
    |
    ├── begin controller invocation
    ├── record the controller-cycle timestamp
    ├── apply the configured delay
    ├── obtain the current robot pose
    ├── compute the next velocity command
    ├── return the generated command
    └── write the internal timing measurements
```

The intentional suspension occurs before the controller obtains the current robot pose and generates the next command.

While the controller is suspended:

* the robot may continue executing the previously published command;
* odometry and laser measurements may continue changing;
* localization and costmap information may continue being updated;
* no new DWA velocity correction is generated;
* the interval between consecutive `/cmd_vel` messages may increase;
* the effective controller frequency may decrease.

## Workspace structure

The experiment is contained in the following catkin workspace:

```text
TurtleBot3/
└── catkin_ws/
    └── src/
        ├── navigation/
        └── turtlebot3_simulations/
```

The T-E5 source-level modification is located inside the ROS Navigation code implementing `DWAPlannerROS::computeVelocityCommands()`.

## How to build the experiment

1. **Select the E5 branch:**

   From the repository root, run:

   ```bash
   git switch turtlebot3/E5
   ```

2. **Source ROS Noetic:**

   ```bash
   source /opt/ros/noetic/setup.bash
   ```

3. **Select the TurtleBot3 Burger model:**

   ```bash
   export TURTLEBOT3_MODEL=burger
   ```

4. **Select the delay condition:**

   Configure the T-E5 delay to one of the following values:

   ```text
   0 ms
   200 ms
   500 ms
   1000 ms
   2000 ms
   ```

5. **Open the catkin workspace:**

   ```bash
   cd TurtleBot3/catkin_ws
   ```

6. **Install missing dependencies, when required:**

   ```bash
   rosdep install --from-paths src --ignore-src -r -y
   ```

7. **Build the workspace:**

   ```bash
   catkin_make
   ```

8. **Source the workspace:**

   ```bash
   source devel/setup.bash
   ```

## How to run the experiment

### 1. Start the Gazebo simulation

Open a terminal, source the environment, and launch the TurtleBot3 world:

```bash
source /opt/ros/noetic/setup.bash
source TurtleBot3/catkin_ws/devel/setup.bash
export TURTLEBOT3_MODEL=burger

roslaunch turtlebot3_gazebo turtlebot3_world.launch
```

Wait until Gazebo has completely loaded the robot and the simulation world.

### 2. Start the navigation stack

Open a second terminal and source the same environment:

```bash
source /opt/ros/noetic/setup.bash
source TurtleBot3/catkin_ws/devel/setup.bash
export TURTLEBOT3_MODEL=burger
```

Launch the TurtleBot3 navigation configuration:

```bash
roslaunch turtlebot3_navigation turtlebot3_navigation.launch
```

### 3. Set the initial pose

In RViz, use **2D Pose Estimate** to assign the predefined initial position and orientation of the robot.

Use the same initial pose for every run and every delay condition.

Wait until the estimated robot pose has stabilized before starting the recording.

### 4. Prepare the output directory

Open a third terminal and create a directory for the selected delay condition.

For example, for the 500-ms condition:

```bash
mkdir -p TurtleBot3_experiments_results/E5/500ms
```

Use separate directories for all conditions:

```text
TurtleBot3_experiments_results/E5/0ms/
TurtleBot3_experiments_results/E5/200ms/
TurtleBot3_experiments_results/E5/500ms/
TurtleBot3_experiments_results/E5/1000ms/
TurtleBot3_experiments_results/E5/2000ms/
```

### 5. Start ROS bag recording

Start the ROS bag recording before sending the navigation goal.

For example:

```bash
rosbag record \
  -O TurtleBot3_experiments_results/E5/500ms/E5_500ms_run1.bag \
  /cmd_vel \
  /odom \
  /scan \
  /amcl_pose \
  /tf \
  /tf_static \
  /move_base/status \
  /move_base/result \
  /initialpose \
  /move_base_simple/goal \
  /clock
```

Change the output path according to the selected delay and repetition.

Examples include:

```text
E5_0ms_run1.bag
E5_200ms_run1.bag
E5_500ms_run1.bag
E5_1000ms_run1.bag
E5_2000ms_run1.bag
```

### 6. Preserve the internal timing CSV

The T-E5 instrumentation generates a source-level CSV containing one row for each instrumented DWA controller invocation.

Before starting the navigation task:

* verify where the T-E5 logger creates the CSV;
* ensure that an old result file will not be confused with the current run;
* remove or rename any previous CSV when required.

After completing the run, move or copy the CSV into the directory associated with the current delay and repetition.

Use a descriptive name such as:

```text
E5_500ms_run1_internal.csv
```

### 7. Send the navigation goal

In RViz, use **2D Nav Goal** to send the predefined project goal.

Alternatively, publish the same goal used by the other TurtleBot3 experiments:

```bash
rostopic pub -1 /move_base_simple/goal geometry_msgs/PoseStamped \
"{ header: { frame_id: 'map' }, pose: { position: { x: 1.3350000381469727, y: 1.3899997472763062, z: 0.0 }, orientation: { x: 0.0, y: 0.0, z: -0.10608347709795334, w: 0.9943572275026757 } } }"
```

The same goal must be used for every run and delay condition.

The effective mission interval begins when the `/move_base_simple/goal` message is published and ends when the corresponding `/move_base/result` message is received.

For runs in which no result is produced, record the observation duration from the goal timestamp to the end of the ROS bag

### 8. End the recording

After the robot reaches the goal or the run reaches the defined termination condition, stop `rosbag record` with:

```text
Ctrl+C
```

Preserve both:

* the ROS bag;
* the source-level timing CSV.

Record whether the run:

* reached the goal successfully;
* failed to produce a navigation result;
* entered a recovery behavior;
* timed out;
* collided with an obstacle;
* showed delayed motion;
* showed overshooting or repeated corrective movements;
* showed frequent stopping;
* presented any other unexpected behavior.

## Number of runs

The final study used the following repetitions:

| Delay condition | Independent runs |
| --------------- | ---------------- |
| 0 ms            | 3                |
| 200 ms          | 3                |
| 500 ms          | 3                |
| 1000 ms         | 3                |
| 2000 ms         | 1                |

The 2000-ms condition is an exploratory extreme case.

Since it contains only one independent run, it must not be treated as evidence of repeatable behavior.

When reproducing the experiment with a different number of repetitions, use:

```text
E5_<delay>_run1
E5_<delay>_run2
E5_<delay>_run3
...
E5_<delay>_runN
```

Before each independent run:

1. restart or reset the simulation;
2. restore the same robot model and simulation world;
3. set the same initial pose;
4. use the same static map and navigation goal;
5. select and verify the intended delay condition;
6. start a new ROS bag recording;
7. generate a separate internal timing CSV;
8. apply the same termination criteria.

## Recorded internal measurements

The DWA controller logger records timing information for each instrumented invocation of `computeVelocityCommands()`.

The measurements are used to derive:

* requested software delay;
* measured software delay;
* delay error;
* interval between consecutive DWA controller invocations;
* DWA controller-cycle temporal displacement.

The measured delay must use a monotonic wall clock around the intentional suspension.

Timestamp extraction and CSV output should remain outside the interval used to measure the intentional delay whenever possible, so that file I/O is not included in the primary timing measurement.

## Recorded ROS topics

The common ROS bag records:

```text
/cmd_vel
/odom
/scan
/amcl_pose
/tf
/tf_static
/move_base/status
/move_base/result
/initialpose
/move_base_simple/goal
/clock
```

These topics make it possible to reconstruct:

* the beginning and end of the navigation task;
* the final navigation result;
* the velocity-command stream;
* the odometric trajectory;
* localization estimates;
* laser measurements;
* TF transformations;
* obstacle proximity;
* recovery and navigation-status events.

## Evaluation metrics

The source-level T-E5 measurements are analyzed together with the common end-to-end navigation metrics.

The primary internal metrics are:

* requested delay;
* measured delay;
* delay error;
* DWA cycle interval;
* DWA cycle displacement.

The externally observable metrics include:

* mission success or failure;
* mission duration;
* observation duration for runs without a result;
* interval between consecutive `/cmd_vel` messages;
* effective velocity-command frequency;
* fraction of almost-zero velocity commands;
* odometric path length;
* commanded linear and angular velocities;
* minimum valid laser range;
* recovery activity;
* collision observations;
* timeouts or missing navigation results.
